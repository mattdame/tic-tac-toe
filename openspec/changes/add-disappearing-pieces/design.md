## Context

See proposal.md — Why. The game is a single-file MakeCode Arcade game (`tic-tac-toe.js`, 160×120, 16-color palette) with a live config panel (3 rows: `PLAY TO`, `X COLOR`, `O COLOR`, drawn into a 130×90 image). Board state lives in `list[9]` (0/1/2 per cell) and `markSprites[9]` (sprite per cell); placement, win, and draw checks all run in the A-button handler and `checkWinning`. Icons are regenerated per player color by `updateMarkImages()` using `image.replace`. Constraints that shape the design:

- Screen is 120px tall and the config panel already uses rows every 18px — space is the tightest constraint for config.
- No alpha blending or smooth scaling; "fade" must be pre-rendered pixel variants.
- Config can be opened mid-match, and the board is not currently reset on config changes.

## Goals / Non-Goals

**Goals:**
- Add a combined `MODE` selector (`5 → 4E → 4H → 3E → 3H`) as a single config row.
- FIFO per-player rotation: oldest piece removed on over-limit placement.
- Gate the board-full draw to `MODE 5` only.
- Fade-by-age indicator in easy modes using removal-distance buckets, identical across `3E`/`4E`.
- Keep `MODE 5` a byte-for-byte behavior match to today's game.
- Make the indicator renderer swappable so other styles (life-ring, next-only) can be tried later.

**Non-Goals:**
- No slide-to-adjacent movement (Three Men's Morris / Teeko variant) — free placement only.
- No AI opponent.
- No indicator variants beyond fade-by-age for this change.

## Decisions

### 1. Combined MODE selector as one config row
One row cycling `5 → 4E → 4H → 3E → 3H`, default `5`. Stored as a single enum value; piece limit and difficulty derived from it.

Rationale: fits the existing panel (4 rows total at ~110px, vs 5 rows that overflow 120px), removes meaningless combos (`5E`/`5H`), and matches the player's stated preference. Alternatives considered: two independent rows (`PIECES` + `EASY/HARD`) — rejected for space and dead combos.

Config panel: grow `drawConfig` from 130×90 to ~130×110, add a `MODE` row, bump `configIndex` cycle from `% 3` to `% 4`. Values display as `5`, `4E`, `4H`, `3E`, `3H`.

### 2. Per-player FIFO queues keyed by board position
Add `queues: {1: number[], 2: number[]}` holding board cell indices in placement order (oldest first). Cleared in `resetBoard`. A piece's "life" is derived from its index in the queue:

```
life(i) = queue.length - i   (0-based i; oldest has life 1 at full queue)
```

Rationale: the board cell (not the sprite) is the stable identity, and removal is trivially `queue.shift()` → clear `list[cell]`, destroy `markSprites[cell]`. Alternatives: store sprites directly — rejected, positions keep board logic (`list`, `checkWinning`) single-source.

### 3. Placement flow with rotation
In the A-button handler, before placing when `MODE` number < 5:

```
if queues[turn].length == N:
    oldest = queues[turn].shift()
    list[oldest] = 0; markSprites[oldest].destroy()
place at cursor; push cursor; mark sprite
refreshFades(turn)
checkWinning(turn)   // on final board state
switch turn
```

Rationale: check win after removal+placement so the final board is evaluated (per spec). At `N == 5` the removal branch is unreachable (a game ends before a 6th placement), so it can stay in the code path or be guarded — either is behaviorally identical.

### 4. Draw gating
`checkWinning`'s board-full loop only declares a draw when the MODE number is `5`; otherwise a no-win board simply continues.

### 5. Fade level maps linearly to remaining life
Each piece has a life equal to the number of the player's placements remaining before removal. A piece's fade is derived from its life by `coverage(life) = 100 - 75·(N - life)/(N - 1)` (percent pixels kept): the newest piece (life = N) is full, the critical piece (life = 1) is at the ~25% readability floor, and every surviving piece deepens exactly one step per placement. Fades apply from the second placement onward — there is no "wait until the limit" gating.

Rationale: the player found the three-bucket model (critical/aging/full) too coarse — it didn't fade until the limit and skipped intermediate steps at `4E`. Per-step fading shows age at a glance from early in the game. The fade range was pushed to a 25% floor to make the age difference more exaggerated. Trade-off accepted: adjacent steps are smaller at `N=4` (coverage 25/50/75/100) than at `N=3` (25/63/100), and the critical piece at 25% is sparse enough that readability must be confirmed on-device. Fade levels are regenerated per mode (piece limit) so the step count matches N.

### 6. Fade variants via dither masking, generated at runtime
For each player color and the current piece limit, generate fade variants for each life level (1..N-1). Faded levels are produced by punching deterministic holes in the icon (hash-threshold pattern, ~N% coverage) using `image` pixel access, keeping shape and color intact so the mark stays identifiable. Regenerated by `updateFadeImages()` on color change (from `updateMarkImages`) and on mode change; a `setImage` swap applies the current level.

Rationale: the 16-color palette has no reliable "darker shade" per player color, and MakeCode has no per-sprite alpha; pixel-hole dithering is the only robust cross-color approach. Alternatives: palette dimming (unreliable per color), `setScale` shrink (not smooth, and shrink was a separate option not chosen).

### 7. MODE changes reset the current board
Changing `MODE` calls `resetBoard()` (clears queues, marks, board) but preserves `Xscore`/`Oscore`/`winTarget`, matching the spec requirement. Color and `PLAY TO` changes keep today's live behavior.

### 8. Indicator renderer behind a swappable seam
Fade application is isolated (a single "apply indicator" function plus per-style variant generation). Later styles (life-ring ticks, next-only pulse) would replace only these, per the player's intent to A/B effects.

### 9. Move-cap draw is hard-coded per mode, not a config row
A per-board total-placement counter (`placements`, incremented on every placement, reset in `resetBoard`) triggers a draw when it reaches a per-mode cap with no winner: **26 at 4 pieces, 40 at 3 pieces** (`moveCap()`). The win check runs before the cap check, so a win on the cap placement still wins. Board-full draw remains gated to `MODE 5`, which ends by move 9 and never reaches its cap.

Rationale for the values: exhaustive simulation of every 4-piece opening showed decided games top out at **26** total placements (8 opening + 18 forced), so capping at 26 catches every endless rotation at the exact point a win is no longer possible without ever truncating a decided game. For 3 pieces, random-play decided games are p95 ≤31 (observed max 72); a cap of **40** converts only extreme drags (~2-3% of games) into draws. Hard-coding was chosen over a config row: the cap is a safety valve, not a gameplay knob, and the panel has no room for a 5th row (4 rows already fill 110 of 120px).

### 10. Auto-place the sole remaining move
When the board has exactly one empty cell and the game is active (a player's turn, config closed, no win in progress, match not over), the current player's piece is placed there automatically after a **~0.8s** delay. This plays out forced endgames without input: the 4-piece rotation tail (each auto-place leaves one empty again, so it cascades) and 5's final move. Implementation is a self-rearming `game.onUpdateInterval(100, ...)` timer: it arms (counts down 8 ticks) only while the conditions hold, cancels immediately otherwise (config open, win animation, match over, >1 or 0 empties), and resets after every placement so the delay between consecutive auto-moves stays consistent. Manual input wins the race: pressing A on the empty cell before the timer fires places it manually and simply restarts the countdown for the next move — no double placement. The cursor is moved to the auto-placed cell for visual coherence.

Rationale: with only one legal move there is no decision left, so waiting for input is pure friction; the short delay lets the player see each rotation (and fade) rather than feeling "beaten" to the cell.

### 11. End-of-game result sequence and continue-on-button
When a board ends in a win, `showWin` records the winning line in a `flashCells` list and a 300ms interval keeps toggling those marks' visibility until the board is reset — the winning line blinks persistently, so the result never disappears while the player looks at it. A draw (placement cap or full board) does not flash: `showDraw` only hides the cursor and the final board simply holds. `declareWinner` arms a **~1.5s** pre-splash hold (`endDelay = 15` ticks) and does not auto-reset afterward — the board stays in its final state and A or B starts the next board (scores preserved), matching the match-over flow. The hold is driven by the same 100ms interval that runs auto-place (a branch that counts `endDelay` down and then calls `showResultSplash`), **not** by a blocking `pause()` — a `pause()` inside a `game.onUpdateInterval` handler blocks the whole main thread, freezing the screen and preventing the flash interval from blinking, so the blink would never be visible during the hold. The continue gate is `awaitingContinue`, set only after the result splash, so a button press during the pre-splash hold is ignored (the `turn == -1` guard in the A/B handlers covers the hold; `awaitingContinue` covers the splash-and-after).

Rationale: the auto-play cascade makes the end abrupt and ambiguous — especially the 26-move cap draw, which previously had no visual cue and was followed by an instant board reset that erased the final position as soon as the splash was dismissed. A persistent win blink plus button-to-continue makes "what happened" readable, and the player asked for the win blink to keep running and for the draw to just hold. The flash only stops when the next board starts.

## Risks / Trade-offs

- **Most-faded piece must stay readable** — [Critical bucket at ~25% pixel coverage could get too dim to read as X/O] → Mitigation: verify on-device; if unreadable, raise the floor (the `75` range / `25` floor constants in `makeFaded`).
- **Panel space is tight** — [4-row panel at 110px leaves little headroom; footer text could crowd] → Mitigation: tighten row spacing if needed; the screen is 120px so ~5px margins remain.
- **Move-cap draws can cut off long decided games** — [At `3` pieces, ~2-3% of decided games run past 40 placements and would now end as draws] → Mitigation: the cap is set to the exact exhaustive maximum for 4 pieces (26), so 4-piece decided games are never truncated; 40 at 3 pieces only affects extreme drags that are near-certainly unwinnable slogs.
- **Auto-place delay is a feel trade-off** — [Too fast and the player feels beaten to the cell; too slow and the forced endgame drags] → Mitigation: 0.8s sits between the 400ms cursor blink and a deliberate tap; manual placement always wins the race, and the delay constant is a single value.
- **Fade legibility at 4 pieces** — [8 faded marks compete for attention at `4E`] → Mitigation: distance-buckets keep only 2 faded pieces per player at any time; the rest stay full.

## Migration Plan

Single file, no data to migrate. `MODE` defaults to `5`, so existing behavior (and any saved preferences) is unchanged until the player changes it. Rollback = revert the MODE value to `5`.
